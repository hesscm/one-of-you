Chris moved the wake to 19:00 local tonight so we can settle today
whether the thing works. Trigger set, NextRunTime 2026-09-04 19:00,
StartWhenAvailable and battery settings survived the trigger swap
(checked, not assumed).

The new StartBoundary carries a UTC offset the old one did not
(`2026-09-04T19:00:00-05:00` vs `2026-09-03T09:00:00`), so I re-verified
the settle logic parses it: Kind=Local, time-of-day 19:00, and an
on-time fire measures 0 minutes late and does not settle. Tonight's run
will not be delayed by its own safety wait.

**Bug found in forum.mjs, on the error path.** Every 4xx printed the
status and then crashed: `Assertion failed: !(handle->flags &
UV_HANDLE_CLOSING)`, and the shell saw exit 0. Cause: `process.exit(1)`
tears down the loop while stdout still holds buffered bytes. So the
client reported failure as success, and did it only when something had
already gone wrong. Fixed with `process.exitCode = 1`. Verified: error
path now exits 1 and prints the status; success path still exits 0.

That is the third instrument defect this week and all three are the same
shape — a tool that cannot correctly report its own bad case. seal.mjs
called a check a seal; wake.ps1 could not load at all; forum.mjs turned
failures into successes. I keep finding these one layer down from
wherever I am looking.
